1. 結論

ネイティブで解決できるのは NHI 課題の 認証方式と権限量に偏る。本丸である ①所有者の特定 ②廃止判断 ③クラウド外NHIの可視化 は両クラウドとも未解決。 「ネイティブで足りるか」は No。ただし NHI インシデントの大半は既にある機能を使い切っていないことに起因し、多くの組織は使い切る前に製品検討へ進んでいる。
  1. 静的シークレットの予防的禁止は Azure が優位。 Entra の application management policy はテナント既定で client secret 作成を禁止し最大寿命を強制できる。AWS の対応物は SCP の iam:CreateAccessKey Deny だけで、既存キーに遡及しない。
  2. 権限の右サイズ化は AWS が優位。 Access Analyzer の unused access(追跡期間 1〜365日で設定可)→ policy generation → custom policy checks は、実使用実績からポリシーを生成し CI で検証できる唯一の完成された導線。
  3. ローテーションは「誰が鍵を持つか」で決まる。 Azure のマネージド ID は有効期間90日の証明書を約45日で自動更新し、閲覧も取得もできない(漏らしようがない)。一方、自分が保有するシークレット(IAM アクセスキー、client secret)を自動ローテーションする機構は両クラウドとも存在しない。周期短縮ではなく保有をやめることが唯一の対策。
  4. 最大の見落としは IMDSv2。 ワークロード資格情報の窃取経路として実績が突出しているのは SSRF 経由のインスタンスメタデータ奪取であり、その唯一の構造的対策が IMDSv2 強制。アカウント既定はリージョン単位のオプトインで、既存インスタンスには適用されない。ここが空いたまま他の NHI 施策を積んでも効果は限定的。
  5. CIEM に空白期がある。 Entra Permissions Management は 2025-10-01 廃止・2025-11-01 サポート終了。Defender CSPM に吸収されたが Permissions Creep Index は廃止。移行を実施していない組織は現在 CIEM 可視性を失っている。

2. スコープ: 何を NHI と数えるか

NHI 対策が失敗する最大の理由は対象集合が合意されていないこと。IAM ロールだけを数えて「棚卸し完了」とする例が多い。

3. 能力マトリクス(21領域)

◎ ネイティブで完結・運用に耐える   ○ 実用水準だが条件・課金・制約付き   △ 部分的・自作の接着剤が必要   × ネイティブに存在しない
#能力領域 AWS Azure / Entra 穴
1ワークロード ID の発行 IAM ロール + インスタンスプロファイル、Lambda / ECS タスクロール、EKS Pod Identity、IRSA◎ マネージド ID(システム / ユーザー割り当て)。Arc でオンプレ VM にも付与可◎ 「作れる」が「既存資産を移行する」導線は無い。主戦場はアプリ改修
2資格情報の保有者 ロールの一時認証情報は AWS 側が発行・失効。保有しない◎ マネージド ID は有効期間90日の証明書を約45日で自動更新。閲覧・取得・手動更新のいずれも不可◎ 両者の最大の価値はここ。「見えない資格情報は漏れない」。ただし適用範囲は自クラウド内に限られる
3外部 / オンプレからの認証 IAM Roles Anywhere(サービスは無料)、OIDC / SAML IdP○ Workload identity federation(FIC)、Arc マネージド ID○ AWS: 信頼アンカーあたり CRL 2件上限(調整不可)、CDP/OCSP 非対応。Azure: FIC は20件上限、flexible FIC はプレビュー
4フェデレーション信頼条件の精度 2026-02 に STS が GitHub / Google / CircleCI / OCI の provider 固有クレームを条件キーとして検証可能に(信頼ポリシーと RCP で使用可、identity-based policy と permission boundary では不可)○ FIC の subject 完全一致のみ。provider 固有クレームの条件評価は無い△ AWS はリポジトリ ID など不変値で固定できるようになったがオプトインで既存ロールには効かない。Azure は 20件上限が緩い subject 設計への圧力になる
5静的キーの予防的禁止 SCP の iam:CreateAccessKey Deny のみ。既存キーには無効△ application management policy でシークレット追加禁止 / 最大寿命 / 証明書寿命をテナント既定として強制。アプリ登録用の applicationRestrictions とサービスプリンシパル用の servicePrincipalRestrictions は別枠で、両方を設定しないと片側が野放しになる。加えて disableLocalAuth 系 Azure Policy(Storage allowSharedKeyAccess、Service Bus cfb11c26-…、Cosmos DB)◎ 両クラウド最大の非対称。 AWS には「シークレットを作らせない」テナント級ポリシーが存在しない
6SP プロパティの改ざん防止 該当概念なし(ロールに資格情報を「追加」する操作が存在しないため不要)— App Instance Property Lock。署名資格情報等の変更をホームテナント外からブロック。unverified: 2026-06 より新規アプリで既定有効○ 既存アプリには適用されない。「既存 SP に資格情報を足す」永続化手法への対策として要個別適用
7トークン窃取耐性(メタデータ) IMDSv2。アカウント既定はリージョン単位で設定、ec2:MetadataHttpTokens を SCP で強制、MetadataNoTokenRejected で移行監視。2024年中頃以降の新インスタンスタイプは IMDSv2 のみ○ Azure IMDS は Metadata:true ヘッダ必須で単純な SSRF を弾く○ AWS はオプトイン、かつ既存インスタンスに遡及しない。 最も費用対効果が高い施策でありながら未適用のまま放置される代表例
8シークレット保管 Secrets Manager、SSM Parameter Store(SecureString)◎ Key Vault、Managed HSM◎ 保管は解決済み。問題は保管庫の外にあるシークレットで、それを見つける機能ではない
9自動ローテーション managed rotation(RDS / Redshift / DocumentDB、Lambda 不要)。2025-11 の managed external secrets で Salesforce / BigID / Snowflake。他は Lambda 自作○ ネイティブ対象は Storage / Cosmos DB のキーのみ。他は Event Grid SecretNearExpiry(期限30日前)+ Function 自作△ ローテーション Lambda / Function 自体が特権 NHI になる点が見落とされる。Key Vault の証明書更新をアプリ登録の資格情報へ反映するネイティブ経路は存在しない
10証明書 / PKI ACM、AWS Private CA。汎用 CA $400/月 + $0.75/証明書、short-lived mode $50/月 + $0.058/証明書(有効期間7日以内)○ Key Vault 証明書(統合 CA で自動更新)。企業 PKI 相当は AD CS / サードパーティ依存△ AWS は CA 単位課金のため「用途別に CA を分ける」正しい設計が高くつく
11インベントリ / 発見 AWS Config、Resource Explorer、list-*。IAM 認証情報レポートは IAM ユーザー専用でロールを含まない○ アプリ登録 / エンタープライズアプリ一覧、Microsoft Graph、マネージド ID 一覧○ いずれも「IAM / Entra に登録されたもの」しか列挙しない。§2 の下3行は原理的に出ない
12所有者(オーナーシップ) 概念が無い。 タグ運用で代替(強制も検証もされない)× アプリ登録の owners 属性。エージェント ID は所有者 / スポンサーを内蔵△ Azure でも退職者が owner のまま残る。OWASP NHI1 が未解決である根本原因
13権限の右サイズ化 Access Analyzer: unused access(追跡期間 1〜365日、$0.20/ロール・ユーザー/月)、policy generation、custom policy checks(CI 組込み可)、external / internal access findings◎ Defender CSPM の CIEM(旧 Entra Permissions Management の後継)△ AWS の対象は IAM ロール / ユーザーのみ。Cognito アプリクライアント、RDS 内 DB ユーザー等は含まれない
14JIT 権限昇格 該当機能なし(ロール切替が代替)× PIM は SP / マネージド ID に「対象(eligible)」割り当てができない。有効化操作を実行できないため。付与できるのは期限付きのアクティブ割り当てまで× PIM を NHI の JIT 統制として提案するのは誤り。両クラウドとも NHI 向け JIT は未実装
15最終利用の可視化 IAM last accessed は直近400日を追跡。Access Analyzer の追跡期間も 1〜365日で設定可(Security Hub 経由の分析器のみ90日固定)◎ SP サインインログ。保持は Free 7日 / P1・P2 30日。Graph API 取得と診断設定による長期保管には P1 以上が必要△ AWS は年次ジョブでも判定できる。Azure は長期退避を先に用意しない限り廃止判断が原理的に不可能
16条件付きアクセス IAM 条件キー(aws:SourceIp / aws:SourceVpce / aws:PrincipalOrgID)+ SCP / RCP による data perimeter○ Conditional Access for workload identities(Workload ID Premium、約 $3/ワークロード/月)△ Azure は単一テナントアプリのみ対象で、マネージド ID と Microsoft 製アプリは対象外。 最も数の多いマネージド ID を CA で守れない
17サービス間認可 VPC Lattice auth policy。SigV4 必須化し vpc-lattice-svcs:SourceVpc / RequestMethod / RequestPath で L7 認可。呼び出し側の identity policy と両方で許可が必要○ アプリロール(app role)+ Entra 認証。サービスメッシュ層の統一機構は無い△ AWS 優位だが VPC Lattice 採用が前提。Azure は個別実装に散る
18権限付与の統制(同意) リソースベースポリシー + sts:ExternalId。第三者への権限付与は IAM ロールに集約○ permission grant policy / authorizationPolicy / 管理者同意ワークフローでユーザー同意を制限し、Graph アプリケーション権限の付与を承認制にできる◎ Entra 側の不正同意付与(illicit consent grant)は NHI の主要侵入経路。ユーザー同意を既定のまま放置している組織が多い
19予防的ガードレール SCP + RCP。RCP は 2024-11 に5サービス(S3 / STS / KMS / SQS / Secrets Manager)開始、上限は組織あたり2,000○ Azure Policy(deny / deployIfNotExists)、application management policy、管理グループ階層◎ RCP のサポート対象サービスはまだ全サービスではない。unverified: 2026-07 時点で20数サービス。「データ境界を張った」と言うには対象外一覧の併記が必須
20異常検知 / 漏洩検出 GuardDuty(Extended Threat Detection の attack sequence は Critical 固定)。公開リポジトリで露出したIAM ユーザーのアクセスキーに AWSCompromisedKeyQuarantine* を適用しサポートケースを起票。Amazon Q Developer のコードレビューがシークレット露出を検出○ ID Protection の workload identity リスク検出(脅威インテリジェンス / 漏洩資格情報 = ダークウェブ・paste サイト・公開 GitHub / 不審サインイン / OAuth アプリへの異常な資格情報追加)。Defender for Cloud のエージェントレスシークレットスキャンが Azure VM / AWS EC2 / GCP のディスクを走査◎ AWS の quarantine はポリシー付与でありキー無効化ではない。 Azure は漏洩検出とディスク走査の両輪で明確に先行。CodeGuru Security は 2025-11-20 サポート終了
21棚卸し / 失効 キー無効化 API、aws:TokenIssueTime による発行済みセッションの一括失効。定期アクセスレビュー機構は無い△ Entra ID Governance のアクセスレビュー(SP 対象、Workload ID Premium 必須)。SP 無効化は accountEnabled=false○ Azure 優位。ただしレビュー担当者は owners が正しい場合のみ機能し、#12 の穴に直結する
読み方: AWS と Azure は得意分野が正反対で、優劣ではなく補完関係にある。 AWS が勝つのは #13 権限の右サイズ化・#15 最終利用の可視化・#17 サービス間認可。Azure が勝つのは #5 静的キーの予防的禁止・#18 同意統制・#20 漏洩検出・#21 棚卸し。 マルチクラウド組織は、Azure の予防ポリシー思想を AWS へ SCP/RCP + CI ガードレールとして移植し、AWS の実績ベース権限削減思想を Azure へ Defender CSPM + 自作レポートとして移植するのが現実解。

NHI8 Environment Isolation同一 NHI を検証と本番で共用 ○ アカウント分離 + SCP/RCP + aws:PrincipalOrgID で構造的に分離 △ アプリ登録はテナント単位のためマルチテナントアプリで容易に境界を跨ぐ 「分離すべき」を強制する検査は両者とも自作
NHI9 NHI Reuse複数アプリで同一 NHI を使い回す × 1ロールを多数のワークロードが引き受けても検知されない × ユーザー割り当てマネージド ID の共有は正常動作扱い 予防も検出も無い。 設計レビューと IaC 静的検査でしか防げない

両クラウドとも「エージェントに ID を与える」ことは解決したが、「そのエージェントが誰の権限で、どのツールを、どの委譲チェーンで呼んだか」を一貫して追える監査面が無い。 AI エージェントは NHI の中で唯一「実行内容が事前に確定しない」種別であり、静的な権限最小化が原理的に効きにくい。 実行時の承認境界(どの操作に人間の承認を挟むか)を設計しない限り、エージェント ID の付与はリスクを移動させただけになる。

6. 構造的欠陥 12項目

致命F-01: 所有者がネイティブに存在しない
AWS の IAM ロールに所有者概念は無く、タグは強制も検証もされないため真実源にならない。Azure は owners を持つ分マシだが、退職者が残る運用が常態化している。 所有者が特定できない NHI は削除判断が下せず、永久に残る。 OWASP NHI1 が未解決である原因はこの1点に集約される。
致命F-02: AWS には「シークレットを作らせない」テナント級ポリシーが無い
Entra の application management policy はテナント既定として passwordAddition 禁止と maxLifetime 強制ができる。AWS の対応物は SCP の iam:CreateAccessKey Deny のみで、粒度も遡及性も劣る。 OWASP NHI7 に対して AWS はネイティブに予防手段を持たない。
致命F-03: NHI の再利用を検出する機構が両クラウドとも無い
1つの IAM ロールを10個のワークロードが引き受けても、1つのユーザー割り当てマネージド ID を10個のリソースが共有しても、両クラウドは正常動作として扱う。 侵害時の影響範囲を最も左右する要因が可視化されていない。 CloudTrail / サインインログの送信元多様性を自前で分析するしかない。
致命F-04: IMDSv2 未強制のまま他の施策を積んでも効果が出ない
ワークロード資格情報の窃取で実績が突出しているのは SSRF 経由のインスタンスメタデータ奪取。唯一の構造的対策が IMDSv2 強制だが、 アカウント既定はリージョン単位のオプトインで、既存インスタンスには遡及しない。 NHI 施策の順序として、権限削減や棚卸しより先にここを閉じるべき。移行状況は MetadataNoTokenRejected で測れる。
重要F-05: 「ローテーションしている」は保有者次第で意味が変わる
Azure のマネージド ID は有効期間90日の証明書を約45日で自動更新し、閲覧も取得もできない。プラットフォームが鍵を保有する限りローテーションは解決済み。 一方、自分が保有するシークレット(IAM アクセスキー、client secret)を自動ローテーションする機構は両クラウドとも無い。 周期短縮に工数を割くより、保有をやめる移行に割くべき。 なお Key Vault の証明書更新をアプリ登録の資格情報へ反映するネイティブ経路も存在しない。
重要F-06: PIM は NHI の JIT 統制にならない
PIM はサービスプリンシパル / マネージド ID に「対象(eligible)」割り当てができない。有効化操作を実行できる主体ではないため、付与できるのは期限付きのアクティブ割り当てまで。 「NHI にも PIM で JIT を効かせる」という設計は成立しない。AWS にも該当機能は無く、NHI 向け JIT は両クラウドとも未実装と扱うべき。
重要F-07: Azure の Conditional Access はマネージド ID に効かない
Conditional Access for workload identities は単一テナントアプリのみが対象で、マネージド ID と Microsoft 製アプリは対象外。 Azure が推奨する本命であるマネージド ID が、Azure の看板統制の保護対象外という構造的なねじれがある。さらに Workload ID Premium は約 $3/ワークロード/月の別課金で、全適用は実務的に高コスト。
重要F-08: Azure ではログ保持を先に手当てしないと廃止判断ができない
Entra サインインログは Free 7日 / P1・P2 30日で、Graph API 取得と診断設定による長期保管には P1 以上が必要。四半期バッチや年次ジョブの NHI を30日窓で「未使用」と誤判定する。 対照的に AWS はこの問題を持たない: IAM last accessed は直近400日を追跡し、Access Analyzer の追跡期間も1〜365日で設定できる(90日固定なのは Security Hub 経由の分析器のみ)。
重要F-09: フェデレーション信頼条件は AWS で改善したが、既存ロールは取り残される
2026-02 から AWS STS が GitHub / Google / CircleCI / OCI の provider 固有クレームを条件キーとして検証できるようになり、リポジトリ ID のような不変値で固定できる(リポジトリ改名・再作成による乗っ取りを封じられる)。 ただしオプトインであり、既に sub をワイルドカードで許している既存ロールは手動で見直すまで危険なまま。信頼ポリシーと RCP でのみ使え、identity-based policy と permission boundary では使えない。 Azure には provider 固有クレームの条件評価が無く、FIC の20件上限が緩い subject 設計への圧力として働く。
重要F-10: 漏洩鍵の自動対応を過信できない(AWS)
AWSCompromisedKeyQuarantine* は AWS が公開リポジトリで露出を検出した際に適用され、サポートケースが起票される。ただし制限ポリシーの付与でありキーの無効化ではない。 自動適用の契機は IAM ユーザーのアクセスキー露出であり、プライベートリポ・CI ログ・チャット経由の漏洩は対象外。「AWS が守ってくれる」という前提は成立しない。 Azure 側は ID Protection の漏洩資格情報検出がダークウェブ・paste サイト・公開 GitHub を対象とし、この領域では明確に先行している。
重要F-11: Private CA のコスト構造が mTLS ベース NHI の設計を歪める
汎用 CA $400/月 + $0.75/証明書、short-lived certificate mode(有効期間7日以内)$50/月 + $0.058/証明書。CA 単位課金のため、用途別・環境別に CA を分割する正しい設計が高コストになる。 加えて Roles Anywhere は信頼アンカーあたり CRL 2件上限・CDP/OCSP 非対応で、失効設計が運用負荷になる。
好材料F-12: クレデンシャルレス化だけは両クラウドとも完成している
IAM ロール / マネージド ID / OIDC フェデレーションを使い切れば、静的シークレットは技術的にほぼゼロにできる。 NHI 課題の大半は「ネイティブに機能が無い」ではなく「既にある機能を使い切っていない」ことに起因する。 製品検討の前に、まず自組織の静的シークレット残存率と IMDSv2 強制率を測ること。この2指標で議論の質が変わる。

7. ターゲット構成

AWS(ネイティブのみ)

  1. IMDSv2 をアカウント既定に設定し(全リージョン)、SCP で ec2:MetadataHttpTokens を強制。既存インスタンスは modify-instance-metadata-options で個別に移行し、MetadataNoTokenRejected がゼロになるまで追う
  2. IAM ユーザーの新規作成を組織全体で禁止し、既存を棚卸しで削除
  3. CI/CD は OIDC に統一。provider 固有クレーム(GitHub なら不変のリポジトリ ID)で信頼条件を固定
  4. 組織レベルの unused access アナライザーを有効化(追跡期間は業務周期に合わせ365日まで延ばす)
  5. custom policy checks を IaC の PR パイプラインに組み込み、権限が広がる変更をブロック
  6. RCP で組織外プリンシパルからのリソースアクセスを遮断(対象外サービスを文書化)
  7. GuardDuty を組織で有効化し attack sequence findings を Security Hub に集約

Azure(ネイティブのみ)

  1. テナント既定の application management policy で client secret の追加を禁止、または最大寿命を強制
  2. アプリ登録は証明書または FIC に統一。FIC の20件上限を前提にアプリ分割の設計指針を先に決める
  3. ユーザー同意を制限し、管理者同意ワークフローを有効化(Graph アプリケーション権限の付与を承認制にする)
  4. Azure Policy で disableLocalAuth / allowSharedKeyAccess=false を deny 強制(サービスごとに個別割り当て)
  5. Entra サインインログを Log Analytics / Sentinel へ長期退避(P1 以上が前提)。これを先にやらないと廃止判断ができない
  6. 重要な SP に Workload ID Premium を割り当て CA と ID Protection を適用。マネージド ID は対象外である事実を設計に織り込む
  7. SP アクセスレビューを四半期で実施。前提として owners を必ず埋める
  8. Defender CSPM を有効化し CIEM とエージェントレスシークレットスキャンを稼働(AWS EC2 も対象にできる)

9. 検証状況と出典

rev.2 での主な訂正(rev.1 の誤りを含む):
  • ログ保持窓に関する指摘を訂正。AWS は IAM last accessed が400日、Access Analyzer の追跡期間も1〜365日設定可のため、rev.1 の「90日窓で誤判定する」は AWS には当たらない。Azure 固有の問題として整理し直した
  • フェデレーション信頼条件を訂正。2026-02 に AWS STS が provider 固有クレーム検証に対応したため、rev.1 の「クラウドは検証しない」は現状に合わない
  • シークレット検出の記述を訂正。Amazon Inspector code security は SAST / SCA / IaC であり、シークレット検出として文書化されているのは Amazon Q Developer のコードレビュー。CodeGuru Security は 2025-11-20 サポート終了
  • AWSCompromisedKeyQuarantine* の適用範囲を訂正(ユーザー・グループ・ロールに付与可能、自動適用の契機は IAM ユーザーキーの露出)
  • sts:SourceIdentity の対応範囲を訂正(AssumeRole / WithSAML / WithWebIdentity すべて、ロールチェーン後も保持)
  • PIM の記述を訂正(SP / マネージド ID に eligible 割り当てはできない)。NHI 向け JIT を独立領域として追加
  • IAM 認証情報レポートの適用範囲を明記(IAM ユーザー専用、ロールを含まない)
  • 追加: IMDSv2、STS provider 固有クレーム、VPC Lattice auth policy、App Instance Property Lock、Entra 同意統制、マネージド ID の資格情報自動更新(90日/45日)、ID Protection の workload identity 検出種別
  • 削除: 再現できない数値を掲げていた成熟度スコアカード、および §3 と重複していたサービス別カタログ2節

一次 / 公式情報で確認した事実

  • Entra Permissions Management: 新規販売終了 2025-04-01(CSP 2025-05-01)、廃止 2025-10-01、サポート終了 2025-11-01。Defender CSPM に吸収、Delinea 提携あり。Permissions Creep Index は廃止され活動ベースロジックに置換
  • Conditional Access for workload identities: 単一テナントアプリのみ、マネージド ID と Microsoft 製アプリは対象外
  • PIM: サービスプリンシパル / マネージド ID に eligible 割り当て不可(有効化操作を実行できないため)。期限付きアクティブ割り当てのみ
  • マネージド ID の資格情報: 有効期間90日、約45日で自動更新、閲覧・取得・手動更新は不可
  • FIC: アプリ / ユーザー割り当て MI あたり20件上限、flexible FIC はプレビュー
  • application management policy: passwordAddition / customPasswordAddition / symmetricKeyAddition の制限と maxLifetime 強制が可能。ポリシーは applicationRestrictions と servicePrincipalRestrictions の 2 系統を持つ(Microsoft Graph の OData メタデータで確認)
  • App Instance Property Lock: 署名資格情報等の変更をホームテナント外からブロック
  • Entra 同意統制: permission grant policy / authorizationPolicy / 管理者同意ワークフロー
  • Key Vault: ネイティブ自動ローテーションは Storage / Cosmos DB のキーのみ。他は SecretNearExpiry(30日前)+ Function。アプリ登録の資格情報を Key Vault から自動更新するネイティブ経路は存在しない
  • Entra サインインログ: Free 7日 / P1・P2 30日。Graph API 取得と診断設定エクスポートには P1 以上が必要(テナントに1本あればよい)
  • ID Protection の workload identity 検出: 脅威インテリジェンス / 漏洩資格情報(ダークウェブ・paste サイト・公開 GitHub)/ 不審サインイン / OAuth アプリへの異常な資格情報追加
  • Defender for Cloud: エージェントレスシークレットスキャンは Azure VM / AWS EC2 / GCP 対象、Defender CSPM または Defender for Servers P2 で GA
  • Azure Policy: Function apps should use managed identity(0da106f2-…)、App Service apps should use managed identity(2b9ad585-…)、Service Bus ローカル認証無効化(cfb11c26-…)
  • IAM Access Analyzer: unused access は $0.20/IAM ロール・ユーザー/月、追跡期間は1〜365日で設定可(プリセット30/60/90)。Security Hub 経由の分析器のみ90日固定。internal access findings の対象は S3 / DynamoDB / RDS
  • IAM last accessed: 直近400日を追跡。認証情報レポートは IAM ユーザー専用
  • IMDSv2: アカウント既定設定は 2024-03-25 から利用可でリージョン単位、既存インスタンスには影響しない。2024年中頃以降の新インスタンスタイプは IMDSv2 のみ。ec2:MetadataHttpTokens を IAM/SCP で使用可、MetadataNoTokenRejected で監視
  • AWS STS: 2026-02 に GitHub / Google / CircleCI / OCI の provider 固有クレーム検証に対応。信頼ポリシーと RCP で使用可、identity-based policy と permission boundary では不可
  • sts:SourceIdentity: AssumeRole / AssumeRoleWithSAML / AssumeRoleWithWebIdentity で指定可、ロールチェーン後も保持
  • ロールチェーンのセッションは最大1時間(EKS Pod Identity のクロスアカウントはロールチェーンを使う)
  • RCP: 2024-11 に S3 / STS / KMS / SQS / Secrets Manager の5サービスで開始、上限は組織あたり2,000
  • EKS Pod Identity: 2025-06 に targetRoleArn でクロスアカウント対応。IRSA は OIDC プロバイダー数と信頼ポリシーサイズが制約
  • IAM Roles Anywhere: サービス自体は無料。信頼アンカーあたり CRL 2件上限(調整不可)、CDP / OCSP コールバック非対応
